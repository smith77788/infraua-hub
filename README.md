## Звʼязок із платформою Palanter

Консоль може передати свою картину — обʼєкти, події та звʼязки живлення разом
із їх походженням — у аналітичну платформу, де вони підпадають під онтологію,
рівні доступу і журнал аудиту. Похідні оцінки (критичність, наслідки відмов)
не передаються навмисно: у платформі вони перераховуються з графа.

Дві змінні середовища **на сервері** вмикають кнопку «Передати картину»:

```
PLATFORM_API_URL=https://<ваш-palanter>.up.railway.app
PLATFORM_API_KEY=<ключ із PLATFORM_API_KEYS>
```

Ключ читається лише в серверній функції й у клієнтський бандл не потрапляє.
Без цих змінних консоль працює як раніше — кнопки просто немає, це штатний
стан, а не помилка.

На боці Palanter потрібно дозволити походження консолі в `CORS_ORIGINS`.

## Перевірка

```
bun install
npm run typecheck   # tsc --noEmit
npm run lint        # eslint + prettier
npm test            # bun test src/
npm run build
```

Тести написані під вбудований рушій Bun (`import { describe, expect, it } from "bun:test"`),
бо цим самим Bun проєкт і збирається. `vitest` у залежностях немає — запуск його
ззовні впаде на всіх файлах, і це не поламані тести, а не той рушій. Спосіб
запуску один: `npm test`.

Тими самими чотирма командами і в тому самому порядку йде CI
(`.github/workflows/ci.yml`), тож локальний прогін означає те саме, що й
перевірка на сервері.

## Розгортання на Railway

Консоль розгортається у двох місцях одночасно, і це навмисно: Lovable збирає
її під Cloudflare Workers, Railway — під Node. Другий шлях потрібен, бо на
ньому буде Telegram Mini App, якому потрібен стабільний власний домен.

Різницю робить одна змінна середовища **на боці Railway**:

```
NITRO_PRESET=node-server
```

Без неї збірка йде під Cloudflare (це типова ціль пресету
`@lovable.dev/vite-tanstack-config`), контейнер не слухає `PORT`, і Railway
віддає 502 при цілком успішній збірці. Саме так це й виглядало спочатку:
статус деплою `SUCCESS`, а сторінка недоступна.

Усередині власного середовища Lovable ця змінна ігнорується — пресет її
навмисно вичищає, — тож увімкнути її на Railway безпечно: збірку для Lovable
вона не зачіпає.

Запуск на Railway: `npm start` (`node .output/server/index.mjs`). Порт бере з
`PORT`, який Railway задає сам.

## Платформа (`platform/`)

Аналітична платформа — онтологія, граф знань із рівнями доступу, ланцюжок
аудиту, пісочниця для обчислень, слідчий агент. Раніше вона жила в окремому
репозиторії `Palanter`; тепер це один продукт і один репозиторій, а `platform/`
— її місце тут.

```
npm run platform:typecheck   # tsc -p platform/tsconfig.json
npm run platform:test        # bun test platform/tests  (203 тести)
npm run platform:build       # компіляція + межа CommonJS
npm run platform:start       # node platform/dist/api/server.js
```

`npm run check` виконує і консоль, і платформу — тими самими кроками, що й CI.

**Чому окремий tsconfig.** Консоль — це ESM зі строгими правилами під браузер;
платформа — CommonJS під Node. Одні налаштування на двох означали б послабити
консоль до рівня, який влаштовує сервер.

**Чому крок збірки, а не просто `tsc`.** У корені оголошено `"type": "module"`
— цього вимагає консоль. Node дивиться на найближчий package.json, тож
скомпільований CommonJS вантажився б як ESM і падав на першому `exports.`.
`platform/build.mjs` кладе у `platform/dist` вкладений package.json із
`"type": "commonjs"` — межа двох модульних систем проходить по каталогу.

Тести платформи не потребують jest: у них немає жодного виклику `jest.*`, тож
вони працюють під вбудованим рушієм Bun, як і решта репозиторію.

Змінні середовища: `PLATFORM_API_KEYS` (JSON-мапа ключ → рівень доступу),
`CORS_ORIGINS`, `PLATFORM_DATA_DIR`, необовʼязково `ANTHROPIC_API_KEY`.

## Telegram-бот

`@Radar_UAbot` живе вебхуком у сервісі консолі, а не окремою службою: йому
потрібен публічний HTTPS-домен, який у консолі вже є, а дані, які він показує,
лежать тут само. Окремий сервіс коштував би грошей і додав би мережевий стрибок
між ботом і його ж фактами.

Точка входу — `POST /api/telegram/webhook`, логіка розбору й текстів —
`src/lib/telegram.ts` (чиста, з тестами).

Змінні середовища сервісу консолі:

```
TELEGRAM_BOT_TOKEN=<токен від @BotFather>
TELEGRAM_WEBHOOK_SECRET=<довгий випадковий рядок>
```

Секрет обовʼязковий. Telegram надсилає його заголовком
`X-Telegram-Bot-Api-Secret-Token`; без перевірки будь-хто, хто знає адресу
вебхука — а вона не таємниця, — може надсилати підроблені оновлення. Незаданий
секрет відхиляє всіх: забута змінна не має тихо відкривати вебхук світові.

Кнопка меню бота відкриває консоль як Mini App, і те саме дає кнопка під
повідомленнями — але **лише в приватному чаті**: `web_app` у клавіатурі групи
Telegram відхиляє разом із усім повідомленням, тож у групі текст іде без
кнопки, з посиланням усередині.

```
curl -X POST "https://api.telegram.org/bot<ТОКЕН>/setChatMenuButton" \
  -H 'Content-Type: application/json' \
  -d '{"menu_button":{"type":"web_app","text":"Консоль","web_app":{"url":"https://<домен>"}}}'
```

Реєстрація вебхука після розгортання:

```
curl -X POST "https://api.telegram.org/bot<ТОКЕН>/setWebhook" \
  -H 'Content-Type: application/json' \
  -d '{"url":"https://<домен>/api/telegram/webhook","secret_token":"<СЕКРЕТ>","allowed_updates":["message","callback_query","inline_query"]}'
```

`allowed_updates` має містити **всі чотири** типи. Бракує `callback_query` — не
працюють кнопки; `inline_query` — бот мовчить у чужих чатах; `edited_message` —
не працює жива геолокація (Telegram шле її оновлення саме як редагування).

Сервіс реєструє вебхук сам (`ensureWebhook`), і з версії з цим текстом звіряє не
лише адресу, а й перелік типів. Раніше звірялася сама адреса — і бот, один раз
зареєстрований на коротший перелік, назавжди лишався без решти оновлень:
Telegram їх просто не доставляв, **не повідомляючи про жодну помилку**. Якщо
щось у боті «не реагує» — почніть з `/api/telegram/setup?secret=…`: у відповіді
є поле `allowedUpdates`, і воно показує, на що бот справді підписаний.

### Як людина задає точку — і чому шляхів три

Запит геолокації в Telegram має щонайменше три способи мовчки не спрацювати, і
всі вони виглядають однаково — «натиснув, нічого не сталося»:

- reply-кнопка `request_location` показується на **всіх** клієнтах, але на
  компʼютері натискання не робить нічого: джерела координат там немає;
- у вікні Mini App браузерний `navigator.geolocation` не працює, а
  `LocationManager` є лише на клієнтах Bot API 8.0+;
- дозвіл можна не дати, відкликати або вимкнути служби місця в системі.

Жоден із цих випадків не є помилкою коду, і жоден не виправляється кодом.
Виправляється інше: щоб людина **ніколи** не лишилась без способу задати точку.

| Шлях | Де працює | Точність |
|---|---|---|
| Вибір області inline-кнопками (`oblast-picker.ts`) | скрізь, без дозволів | центр області — десятки км |
| `/my Харків` | скрізь | центр області |
| Кнопка «📍 Точніше» → геолокація | телефон | точна |
| 📎 → Локація → точка на карті | телефон і **компʼютер** | точна |
| Жива геолокація | телефон | точна, їде за людиною |

Основним став перший — єдиний, який не може не спрацювати. Решта поруч, із
чесною позначкою, де саме вони працюють. Грубість вибору області не
замовчується: після вибору бот прямо каже, що це орієнтир на десятки
кілометрів, і як задати точніше.

**Якщо в боті щось «не реагує»** — надішліть йому `/stats` (команда власника).
Він покаже адресу вебхука, типи оновлень, на які бот підписаний, чого бракує,
чергу й останню помилку доставки. Бракує типу — Telegram не доставляє цей клас
оновлень і **не повідомляє про це нічим**.

### Геолокація в Mini App

Усередині вікна Telegram `navigator.geolocation` **не працює**: у власному
WebView немає браузерного діалогу дозволу, тож виклик мовчки відхиляється, а
подеколи не кличе жодного зворотного виклику взагалі — кнопка просто зависає в
стані «визначення…». Правильний шлях — `WebApp.LocationManager` (Bot API 8.0+),
і його обов'язково треба `init()` перед першим використанням.

Обгортка лежить у `src/lib/telegram-webapp.ts` і зроблена так, щоб людина
ніколи не лишилась у глухому куті: кожен зворотний виклик обмежений строком,
причина відмови називається окремо (немає служб місця / доступ не надано /
Telegram не відповів), для «доступ не надано» показується кнопка, що відкриває
налаштування доступу, а поза Telegram усе падає на звичайний браузерний запит.
Вибір області руками лишається доступним завжди.

### Куди летить ціль: оцінка замість прямої лінії

Головне питання продукту («чи летить на мене») відповідалось однією прямою:
береться поле `heading` від джерела, береться табличка типових швидкостей —
і ціль ведеться по лінійці. Саме тому ETA доводилось різати на годині.

Але пряма була неправдою не лише на годині. Вона була нею завжди — просто на
п'ятій хвилині помилка ще не встигала вирости. Проблема не в горизонті, а в
тому, що оцінка **не мала похибки**: «~22 хв» і «22 хв» виглядають однаково,
хоч перше могло означати «від 14 до 35».

**`track-filter.ts`** — курс і швидкість більше не беруться на віру, а
виводяться з послідовних фіксів тієї самої цілі; розкид між цими фіксами й дає
похибку. Невпевненість тут не налаштована константою — вона **заміряна на самих
даних**. Ціль ведеться не лінією, а розподілом: уздовж курсу невизначеність
росте від похибки швидкості, впоперек — від похибки курсу й від спостереженого
розвороту.

Три речі, яких пряма не вміла:

- **циркулярне середнє курсів** — арифметичне дає між 350° і 10° рівно 180°,
  тобто ціль, що летить назад;
- **відсів помилок ототожнення** — два звіти про «ту саму» ціль із різних
  областей дають 900 км/год для шахеда; це не прискорення;
- **чесний поділ походження** — курс `observed` (з руху), `reported` (з чужого
  поля) і `none` (немає); оцінка на чужому твердженні не виглядає такою ж
  певною, як на власному спостереженні.

**`approach.ts`** — класична задача про найближче зближення (CPA), тільки по
розподілу, а не по прямій. Точка людини розкладається на складову **вздовж**
траєкторії (звідси час, із вилкою) і **впоперек** (звідси промах і шанс пройти
ближче за радіус тривоги, з нормального розподілу).

Це прибрало ваду, через яку народжувалась половина зайвих сповіщень: сектор
±60° зараховував як «іде на вас» ціль, що промине за тридцять кілометрів.
Тепер промах рахується, і в картці видно різницю між «на вас» і «повз вас».

Радіус спостереження («що я хочу бачити», 50–100 км) і радіус тривоги
(«наскільки близько — це вже близько», 15 км) розділені: злиті, вони дали б
шанс «пройде ближче за сто кілометрів», який справджується майже завжди.

**Де межа.** Далі без НОВИХ ДАНИХ не пройти. Ми маємо позиції, які хтось
побачив і встиг повідомити, з точністю до населеного пункту й частотою в
хвилини. Кращу оцінку дає не кращий алгоритм, а радар або ADS-B — інший клас
джерела. Усе, що можна вичавити з наявних спостережень, вичавлено; далі
починається вигадування.

### Стеля, з якої випливає архітектура розсилки

Telegram документує для розсилки **~30 повідомлень на секунду**
([Bots FAQ](https://core.telegram.org/bots/faq)). Платні розсилки піднімають це
до 1000/с, але вимагають 100 000 Stars на балансі бота й 100 000 активних
користувачів на місяць.

Отже безкоштовно: 100 000 підписників — **близько 56 хвилин** на одне
сповіщення. Для повітряної тривоги це не затримка, а відмова: шахед за той час
долає 165 км. **Персональне сповіщення не масштабується так, як канал** — один
пост доходить до будь-якої кількості читачів одним запитом.

Це головна властивість системи, і вона визначає три рішення:

1. **Пріоритет замість порядку у файлі.** Бюджет витрачається спершу на тих,
   кому в укриття. Коли черга довша за бюджет, ріжеться хвіст із найнижчим
   пріоритетом — а не випадкові люди в кінці масиву, як було.
2. **Строк придатності.** «~4 хв до вас», доставлене через двадцять хвилин,
   гірше за мовчання: воно бреше про час. Прострочене не надсилається й
   рахується як втрата, а не як успіх.
3. **Повага до 429.** Поодинокий виклик може сам перечекати й повторити; виклик
   із черги — ні: 429 означає, що перевантажений бот цілком, тож `retry_after`
   зупиняє **всю** чергу.

`/stats` показує стелю числами й мовчить, поки запасу вистачає: попередження
про межу, до якої ще далеко, перетворюється на фон.

### Хто взагалі під загрозою: просторовий індекс

Обхід підписників був O(підписники × цілі) — відстань від кожного до кожної.
Майже вся ця робота марна наперед: наліт стоїть над кількома областями.

Питання перевернуте: не «які цілі поруч із людиною», а «хто поруч із ціллю».
Підписники розкладаються по сітці **рівнями радіуса** — хто просив 25 км, не
перевіряється на сотні.

Заміряно (підписники по містах, хвиля з 18 цілей над двома областями):

| Підписників | Повний перебір | Індекс | Кандидатів із усіх | Знайдено |
|---|---|---|---|---|
| 10 000 | 11 мс | 5 мс (+8 мс побудова) | 1 904 | 653 / 653 |
| 100 000 | 57 мс | 19 мс (+22 мс) | 18 905 | 6 521 / 6 521 |
| 1 000 000 | 593 мс | 229 мс (+179 мс) | 188 831 | 65 169 / 65 169 |

Збіг із повним перебором точний — це перевіряє тест, а не спостереження.

Межа названа прямо: коли цілі стоять по всій країні, відсіювати нема чого, і
індекс лише додає роботи (заміряно: 1 224 мс проти 2 784 мс на синтетичному
гіршому випадку). Але тоді вузьке місце вже не процесор — мільйон сповіщень на
30/с це дев'ять годин, на три порядки більше за будь-яку економію тут.

### Гейт підписки на канал

Канал і бот — одне ціле: у каналі загальна картина, у боті персональна. Тому
радар відкривається тим, хто в каналі. Вмикається сам, щойно
`TELEGRAM_CHANNEL_ID` заданий як `@username` (бот при цьому має бути
адміністратором каналу — він і так ним є, щоб постити).

Це інструмент безпеки, тож у конструкції закладені три запобіжники, і жоден не
можна прибрати «для простоти»:

1. **Гейт відмовляє у бік доступу.** Не вдалося перевірити членство (Telegram не
   відповів, бот не адміністратор, канал заданий числовим id) — пускаємо. Збій
   на нашому боці не має коштувати комусь сповіщення про ціль.
2. **`/stop` і пауза сповіщень ніколи не гейтяться.** Право замовкнути бота не
   може залежати ні від чого.
3. **Уже налаштовані сповіщення не вимикаються заднім числом.** Хто задав точку
   й потім вийшов з каналу — далі отримує попередження. Тихо перестати
   попереджати того, кого вже попереджали, — найгірший спосіб карати за
   відписку.

`/help`, `/status` і `/start` теж відкриті: людина має спершу зрозуміти, про що
взагалі мова.

### Персональний радар: «чи летить на мене»

Це відповідь на питання, якого не ставить жоден інший монітор цієї ніші. Вони
кажуть, що в небі над областю; людині ж треба знати, чи йде це **на неї**.

Людина надсилає точку (кнопкою, вкладенням або `/my Харків` — тоді береться
центр області), і бот рахує для цієї точки напрямок, відстань і хвилини до
підльоту кожної вхідної цілі. Далі він **пише сам**, коли на точку заходить
нова ціль: обхід підписників іде кожні 90 секунд — крок каналу тут не годиться,
бо шахед за пʼять хвилин проходить третину усталеного радіуса.

| Файл | Що в ньому |
|---|---|
| `src/lib/subscribers.ts` | коли будити, а коли мовчати — чиста функція `decideAlert` |
| `src/lib/subscriber-store.ts` | сховище підписок (JSON на диску) |
| `src/lib/bot-personal.ts` | картка, сповіщення, налаштування, кнопки |
| `src/lib/referral.ts` | посилання-запрошення і облік переходів |
| `src/lib/bot-inline.ts` | inline-режим: картка обстановки в чужий чат |

Рішення «будити чи ні» винесене в чисту функцію навмисно: помилитися тут дорого
в обидва боки. Промовчати про вхідну ціль — не спрацювати тоді, коли єдиний раз
і треба; розбудити зайвий раз уночі — і бота вимкнуть, після чого він не
спрацює вже ніколи. Тому нічний режим **лише звужує** денний і ніколи не
розширює, поверх дедупу за цілями стоїть жорстка часова підлога, а ескалація
рівня небезпеки пробиває будь-яку паузу.

#### Де лежать підписки

**Без постійного тому вони зникають при кожному редеплої.** На Railway це
лагодиться одним кроком:

1. сервіс консолі → **Volumes** → **+ New Volume**;
2. шлях монтування — `/data`;
3. дочекатись перезапуску.

Змінну задавати не треба: Railway сам виставляє `RAILWAY_VOLUME_MOUNT_PATH`
щойно том підключено ([Railway → Volumes](https://docs.railway.com/reference/volumes)),
і бот бере шлях звідти. `BOT_DATA_DIR` лишається як перекриття — для випадку,
коли том ділять із чимось іще.

#### Якщо тому немає: копія в чат власника

Резервна копія підписників іде файлом в **особистий чат власника з ботом** —
щодня о 9:00 разом із підсумком доби, або на вимогу командою `/backup`.

Куди саме — важливо: особистий чат, не канал і не сторонній сервіс. Це та сама
межа довіри, що й сам бот: дані вже в нього є, і нових місць, де лежать чужі
координати, не з'являється.

Відновлення — переслати цей файл боту. Воно **зливає**, а не перезаписує:
людина, яка підписалась після копії, не зникає через те, що власник відновив
учорашній файл. Живий запис завжди сильніший за архівний.

Це не заміна тому, а страховка від класу відмов, від якого том не рятує:
видалений сервіс, том, змонтований не туди, помилкове очищення.

Через 45 секунд після старту бот **сам** перевіряє сховище й пише власникові,
якщо воно ефемерне або в нього не пишеться. Один раз на процес: попередження,
яке повторюється щогодини, перестає бути попередженням. Мовчання після
перезапуску означає, що з томом усе гаразд.

`/stats` показує не лише шлях, а й **звідки він узявся** і **результат
справжньої спроби запису**. Останнє важливе окремо: всі попередні висновки про
сховище були висновками з наявності змінної, а том можна підключити не в ту
теку або лише для читання — конфігурація виглядатиме правильною рівно доти,
доки хтось не помітить, що підписники зникли.

Inline-режим доводиться вмикати руками в @BotFather (`/setinline`) — Bot API
методу для цього не має. Поки не увімкнено, Telegram просто не надсилає
`inline_query`, і код про це не дізнається.

### Передтривога: попередження раніше за сирену

Дзеркало правила про відбій, і разом вони утворюють симетрію, на якій усе
тримається:

- **поспішити з попередженням безпечно** — найгірше, що станеться, людина дарма
  зайде в коридор на кілька хвилин раніше;
- **поспішити з відбоєм смертельно** — людина вийде з укриття, коли ще летить.

Тому відбій чекає на офіційне оголошення, а попередження — ні. Коли ціль іде на
точку, а офіційної тривоги в цій області ще немає, бот пише **передтривогу** —
і прямо називає її передтривогою: «Тривога!» від нас там, де офіційної немає,
це підміна повноважень, після якої людина не повірить справжній сирені.

Коли сирену нарешті вмикають, бот звітує заміряним числом: «ми попередили вас
на 6 хв раніше». Не обіцянкою «ми швидші», а фактом по кожному конкретному
разу — і тільки в діапазоні 1–30 хв, поза яким це або збіг, або не наша
заслуга (findings №45).

### Вухо як датчик: читачі стають мережею спостереження

OSINT-канали пишуть про ціль, коли її хтось **побачив і встиг написати**. Але в
ту саму хвилину дрон **чують** сотні людей — і ця інформація просто зникає.

Кнопка «👂 Чую» під кожною карткою перетворює її на дані. Сто тисяч читачів —
це сто тисяч мікрофонів, і жодного обладнання для цього не треба.

Конструкція протистоїть натовпу, а не покладається на нього: **жоден окремий
доклад ніколи нічого не піднімає**. Підтвердженням вважається лише збіг
кількох *різних* людей у тому самому місці й часі (15 км, 12 хвилин). Один
зляканий або зловмисник не може створити подію в принципі — і рахуються різні
`chatId`, а не натискання: десять докладів однієї людини це одна людина.

### Коло: «я в порядку» замість двадцяти дзвінків

Уся ніша одномісна — монітор каже людині про людину. Але після кожного удару
відбувається те саме: мільйони одночасно пишуть «ти як?» рідним, мережа лягає,
відповідь іде двадцять хвилин, і ці двадцять хвилин найгірші в добі.

Кілька людей заводять коло за кодом, і після тривоги кожен одним дотиком каже
«я в порядку». Межі взято свідомо:

- коло **не показує нічиїх координат** — лише імʼя, яке людина сама назвала, і
  час відмітки. Місце розташування рідних — саме те, чого не можна зливати в
  чат, який можна переслати;
- **мовчання не тлумачиться**. Порожня позначка означає «людина не тиснула
  кнопку», і це сказано в екрані прямим текстом: розряджений телефон, сон,
  немає мережі. Припущення тут коштувало б комусь ночі жаху на порожньому місці.

### Точка, що їде за вами

Телефон людини в дорозі — у поїзді, в авто — знає, де вона, а радар за
збереженою точкою рахує для міста, з якого вона виїхала вранці. Telegram уміє
живу геолокацію: бот приймає її оновлення (`edited_message`) і тихо пересуває
точку, нічого не пишучи — оновлення приходять щохвилини, і балакучий радар тут
був би гіршим за мовчазний.

### Наскільки цьому вірити — у самому сповіщенні

Модулі верифікації (`advisory.ts`, `source-credibility.ts`) у проєкті були
давно, але жодна відповідь бота їх не показувала: людина бачила «шахед за
12 км» і не могла знати, чи це три незалежні канали, чи одне непідтверджене
повідомлення. Тепер підстава стоїть у самому сповіщенні — бо це різні рішення,
а о третій ночі часу шукати довідку немає.

У каналі те саме: область, де **всі** цілі спираються на одне непідтверджене
джерело, позначена «❓ одне джерело». Часткова слабкість не позначається —
«частково непідтверджено» читач однаково прочитає як «непідтверджено», і
позначка знеціниться для випадків, коли вона справді щось означає.

## Telegram-канал: хвиля замість стрічки дублів

Канали цієї ніші влаштовані однаково: кожні кілька хвилин новий пост із тим
самим переліком областей. За ніч це 60–80 повідомлень, серед яких уранці нічого
не знайти, — і саме тому такі канали читають «без звуку» або вимикають.

Тут наліт — це **одна хвиля** з початком, розвитком і відбоєм
(`src/lib/channel-wave.ts`):

1. **Живий пост.** Поки хвиля триває, редагується один пост — разом із
   картинкою, а не лише підписом: свіжий текст під застарілою картою гірший за
   мовчання, бо виглядає як щойно перевірений. Новий пост відкривається тільки
   тоді, коли є привід: початок хвилі, поява критичного типу (балістика там, де
   були шахеди) або те, що живому посту вже понад 45 хвилин.
2. **Прогноз.** Курс і типова швидкість у даних уже є, тож область, у яку цілі
   ввійдуть за 10–30 хвилин, називається до того, як вони туди дійдуть:
   «🔮 за курсом далі: Полтавщина (~11 хв)». Це прогноз, і в тексті він так і
   названий — ціль веде по прямій, а цілі маневрують; горизонт тому обмежено
   пів годиною.
3. **Відбій — тільки після офіційного оголошення.** Не тоді, коли ми перестали
   бачити цілі. Наші дані — повідомлення спостерігачів, а не радар: ціль, якої
   ми не бачимо, не перестає летіти, і людина, що вийшла з укриття за нашим
   постом, вийшла з нього рано. Тому відбій виходить лише коли офіційну тривогу
   знято в **усіх** областях, яких торкалася хвиля (джерело — ubilling, те саме,
   що живить `/status`), і лише якщо та тривога взагалі оголошувалась: «відбій»
   без тривоги — це відбій чого?

   Поки тривога триває, а цілей уже не видно, живий пост переписується на
   чесний стан і прямо каже, що це **не** відбій. Це найважливіший текст у
   каналі: у читача на екрані пост із переліком цілей, яких уже немає, і тишу
   навколо найлегше прочитати як дозвіл вийти.

   Три стани, а не два: якщо джерело офіційних тривог не відповідає, канал
   мовчить. Відбій, виданий наосліп, гірший за відсутність відбою. Якщо ж
   тривога не знімається понад 12 годин (є області, де вона триває добами),
   хвиля закривається мовчки — без поста, який прочитали б як відбій.

   Те саме правило діє й у боті: картка `/my` не скаже «спокійно, можна спати»
   під чинною тривогою — це той самий фальшивий відбій, тільки сказаний одній
   людині й тому ще переконливіший.
4. **Підсумок доби** о 9:00 за Києвом. Тиха доба поста не отримує.
5. **Кнопка під кожним постом** — «🎯 Чи летить на мене?». Вона їде разом із
   пересиланням: хто б куди не переслав зведення, кнопка лишається робочою, і
   читач чужого чату одним дотиком отримує власний радар. Плюс хештеги
   (`#Сумщина #шахеди`), за якими канал знаходять у пошуку Telegram ті, хто про
   нього ніколи не чув.
6. **Шлях, а не крапка.** Усі монітори малюють позначку зі стрілкою — і читач
   добудовує пряму лінію на своє місто. Насправді шахед крутить: заходить із
   півночі, розвертається, обходить ППО. На картинці тепер видно **спостережений
   трек** — тільки те, що ми реально бачили, і ніколи не добудований уперед:
   продовження лінії за останню відому точку було б вигаданим маршрутом із
   виглядом заміряного.
7. **Уночі дзвенить лише те, заради чого варто прокинутись.** Оновлення по
   шахедах ідуть без звуку (пост є, дзвінка немає), ракети й балістика дзвенять
   завжди. Це різниця між каналом, у якого ввімкнені сповіщення, і каналом, у
   якого їх вимкнули всі.
8. **Реконструкція ночі.** Під відбоєм — не порожня карта, а картинка всіх
   шляхів, якими пройшла хвиля, і маршрут рядком: «🛣 Чернігівщина → Київщина
   (+35 хв) → Житомирщина (+1 год 12 хв)». Час від початку хвилі, а не
   годинником: «+35 хв» читається і через тиждень.
9. **Англомовне дзеркало.** Найбільша аудиторія цієї ніші, до якої ніхто не
   дотягується, — поза країною: кореспонденти, аналітики, діаспора. Вони цитують
   українські монітори щодня й читають їх машинним перекладом, який плутає
   «крилаті» з крилами. Дзеркало не перекладає: **той самий генератор складає
   англійський пост із тих самих чисел** (`channel-lexicon.ts`). Тому англійська
   версія не може назвати іншу кількість цілей — розбіжність між мовами тут
   неможлива за побудовою, а не за домовленістю.

## Що на Railway

Два сервіси в одному проєкті, обидва з цього репозиторію:

| Сервіс | Що це | Збірка |
|---|---|---|
| `infraua-hub` | консоль + вебхук бота | Railpack, `NITRO_PRESET=node-server` |
| `platform-api` | API платформи | `Dockerfile.platform` |

`platform-api` створено через API, тож у нього **немає автоматичного розгортання
на push** — тригер створюється лише з інтерфейсу Railway (`deploymentTriggerCreate`
project-токену недоступний). Доки його не додано, платформа розгортається
вручну: у Railway кнопкою Deploy, або мутацією
`serviceInstanceDeploy(..., latestCommit: true)`.

Прапорець `latestCommit` тут не дрібниця: без нього Railway перезбирає останній
*відомий* йому коміт, а не свіжий, і три збірки поспіль падали на вже
виправленій помилці.

Стан платформи (граф, аудит, справи) лежить на томі Railway, змонтованому в
`/data` — те саме значення в `PLATFORM_DATA_DIR`.

### Хто читає: рівень, коло, особа

Рівень доступу (`ClearanceLevel`) відповідає лише на питання «наскільки високо».
Це субординація, а не правило поширення: аналітик із рівнем SECRET бачив усе
SECRET у системі, хоча топологія мережі одного оператора, персональні дані його
персоналу і справа про закупівлю — три різні кола «треба знати».

Тому позначка тепер складається з двох частин: рівень і **компартменти**
(`platform/core/security/Marking.ts`). Читач бачить факт, якщо він допущений
**не нижче** рівня **і** входить у **кожне** коло на цьому факті.

Ключ описується у `PLATFORM_API_KEYS` у двох формах — обидві підтримуються:

```json
{
  "ключ-1": "SECRET",
  "ключ-2": {
    "principal": "olena",
    "clearance": "SECRET",
    "compartments": ["grid-topology"],
    "purposes": ["outage-response"]
  }
}
```

Коротка форма не застаріла — це правильна форма для службового ключа, і саме її
використовують наявні розгортання. Вона дає допуск того ж рівня, **жодного**
кола і власника, названого хешем самого ключа. Тобто оновлення платформи не
змінює мовчки, хто що читає, і не вписує старий ключ у всі кола одразу.

Запис можна позначити лише тим колом, у яке входить сам автор запису. Інакше
можливі два збої, і другий гірший: вигадане коло робить дані нечитними взагалі
(діра в графі, не відрізнна від втрати даних), а запис у чуже коло означає
писати факт, якого ти сам ніколи не побачиш, щоб перевірити.

### Навіщо робиться запит, і що з цього записано

Рівень доступу каже, що людині дозволено бачити. Він не каже, чи цей конкретний
перегляд був частиною її роботи, — а зловживання живе саме там: аналітик із
допуском до мережі, що дивиться підстанцію свого сусіда, лишається в межах
допуску й поза межами роботи. Жодна перевірка за рівнем цього не побачить.

Тому запит може нести заявлену причину заголовком:

```
X-Access-Purpose: outage-response
```

Призначення **не** відкриває даних — це не другий рівень доступу. Воно
привʼязує запит до названої причини, відхиляє причини, під які цей ключ не
видавали, і записує причину в ланцюг аудиту поруч із тим, що повернулося.
Виявлення, не запобігання — і це чесний опис, через який воно коштує заголовка,
а не перебудови.

Перелік причин — у `platform/config/security_policies.json`. Прапорець
`require_purpose` типово вимкнений: увімкнути його, поки жодному ключу не
видано призначень, означало б одномоментно закрити всі ключі від усіх
маршрутів, а контроль безпеки, впровадження якого виглядає як аварія, просто
вимикають. Ключ із власним переліком `purposes` тримається його в будь-якому
разі, тож перехід робиться ключ за ключем.

**Кожне читання тепер у журналі.** Досі ланцюг тримав те, що робили агенти, і
нічого про те, що бачили люди: `GET /api/platform/graph` не лишав жодного
сліду, тож питання «хто вивантажив перелік підстанцій і за яким дорученням»
відповіді не мало. Записується форма відповіді — маршрут (шаблон, без
ідентифікаторів і пошукових рядків), причина, рівень, кола і **кількості**, —
але ніколи сам вміст: журнал, що копіює описувані дані, є другою, гірше
захищеною копією цих даних.

Через це `GET /api/platform/audit` став сторінковим:
`?limit=&before=&actor=&action=`. Перевірка ланцюга (`verification`) охоплює
**весь** журнал, а не сторінку: сторінка, що сходиться, поки змінено давніший
запис, — хибне заспокоєння.

### Стоячі запити: питання, яке не треба ставити вдруге

Консоль уже зіставляє повітряні загрози з обʼєктами — покадрово, у браузері,
і все зникає при перезавантаженні. Це **подання**, а подання не може сказати,
що щось почало мати значення, поки ніхто не дивився.

Стоячий запит — умова, покладена на зберігання й переобчислювана щоразу, коли
надходять дані (`platform/core/alerts/`). Спрацювання потрапляє в чергу
розбору зі станами `new → acknowledged → resolved`: хто ще не дивився, хто
взяв, хто закрив і чому. Ці три відповіді й перетворюють потік подій на
роботу, яку можна передати наступній зміні.

Умови — дані, а не код (`platform/config/alert_rules.json`). Те, заради чого
варто розбудити людину, — операційне рішення оператора, воно змінюється
щотижня і не має чекати на випуск. Кожне спрацювання повертається з доказом:
рядками, які кажуть, **чому саме цей обʼєкт**. Сповіщення, яке не можна
розібрати, привчає відхиляти його — а далі відхиленим буде й те, що спрацювало
правильно.

Дедуплікація — різниця між чергою і потопом: умова, що продовжує триматися
(підстанція нікуди не поділася з-під геозони), збільшує лічильник наявного
запису, а не створює новий. Закритий запис лишається закритим протягом
«тиші» (`reopenAfterMinutes`) і відкривається знову, лише якщо умова
спрацювала після неї — повторення це новина, миготіння ні. Вручну відкрити
закритий запис не можна: відкриває його факт про світ, а не натискання.

Позначка сповіщення — підлога правила, піднята до позначки обʼєкта, що
спрацював. Спостереження саме є формою доступу, тому правило бачить коло,
лише якщо саме в нього вписане, а вписати його може лише автор, який у цьому
колі є. Наслідок названий прямо: закриті дані не під наглядом, доки хтось
зсередини кола не напише для них правило.

```
GET  /api/platform/alerts?state=new&minSeverity=high
GET  /api/platform/alerts/rules
POST /api/platform/alerts/rules              # CONFIDENTIAL і вище
POST /api/platform/alerts/evaluate
POST /api/platform/alerts/<id>/acknowledge
POST /api/platform/alerts/<id>/resolve
```

### Три квадратичні місця

Заміряно на синтетичних наборах розміру українського (4109 підстанцій — це
лише одна категорія):

| Місце | Було | Стало |
|---|---|---|
| Розвʼязання дублікатів, 4000 сутностей | 116 с | 0.2 с |
| Пошук, 5000 документів × 20 запитів | 913 мс | 95 мс |
| Зіставлення за близькістю, 10 500 вузлів | квадратичне | 71 мс |

Перше — не «погано масштабується», а відмова в обслуговуванні власному
маршрутові `/api/platform/analytics`, який викликає це на кожен запит.

Прискорення тут нічого не варте без доказу, що воно нічого не втратило, тож
у кожному випадку тест порівнює швидкий шлях із повільним:

- резолвер — з повним перебором тих самих пар тією ж функцією оцінки;
- пошук — із наївним косинусом, побітово (`toBeCloseTo(…, 10)`);
- гео-індекс — із повним скануванням, на пʼяти радіусах і через межу комірки.

Блокування може відкинути ключ, який перестав розрізняти («підстанція» є в
кожній назві). Це навмисно й **повідомляється** у `resolution` разом із
відповіддю: резолвер, який тихо перестав шукати, гірший за повільний.

### Закупівлі: джерело для половини онтології, яка його не мала

`AWARDED_CONTRACT` і `HIDDEN_BENEFICIARY_OF` існували в онтології з самого
початку, а `self_dealing_pattern` важив 35 балів — найбільше у файлі сигналів.
Джерела не було в жодного. Половина моделі ризику оцінювала звʼязки, які
структурно не могли зʼявитися: смуги й рейтинги рахувалися ні по чому.

Prozorro закриває цю половину. Джерело відкрите, ключа не потребує, і його
записи несуть те, чого не дає зіставлення назв, — код ЄДРПОУ, тобто справжню
тотожність юридичної особи. Вузли ключуються `org:edr:<код>`: та сама компанія
трапляється в цих записах у кількох написаннях, і всі вони — один
зареєстрований субʼєкт.

```
POST /api/platform/ingest/prozorro        # записи, які вже є на руках
POST /api/platform/ingest/prozorro/pull   # витягти вікно з фіду, CONFIDENTIAL
```

Тягне платформа лише на запит: планувальник потребує блокування, а блокування
між перезапусками Railway немає — два примірники, що обходять те саме вікно,
подвоїли б кожну суму в `value_concentration`, і ніщо не виглядало б зламаним.

Присудження — **ребро** з сумою, а не вузол-подія. Це не смак: сигнал
`value_concentration` підсумовує властивість `amount` по ребрах сутності, тож
записане інакше присудження було б невидиме для оцінювання, заради якого фід і
підключався.

Перевірено на 100 справжніх тендерах, і саме це виявило дві помилки, які
синтетичні дані не показували б ніколи: токенізатор пошуку різав українські
слова (знахідка №17), а обидва структурні сигнали ризику вироджувалися на
розрідженому графі (№18). Фікстура в `platform/tests/fixtures/` — теж справжні
записи: форма, яку я вигадав би сам, перевіряла б лише мою уяву.

### Дві осі часу

Граф зберігав лише теперішнє: `upsertNode` перезаписував властивості на місці,
`retractSource` видаляв. Через це три питання, на які така система має
відповідати, відповіді не мали:

- **Що ми знали чотирнадцятого, коли ухвалювали рішення?** Не що відомо
  *зараз* про чотирнадцяте, а що справді було перед аналітиком тоді.
- **Що змінилося з учора?** Картина без попередньої версії дає лише «подивіться
  ще раз і скажіть, чи щось впало в око».
- **Чи можна відтворити цю знахідку?** Справа закріплювала номер у журналі
  аудиту, але граф під нею вже поїхав, і повторний прогін давав інший висновок
  із тим самим походженням.

Осі дві, і плутати їх не можна. **Час запису** — коли платформа дізналася.
**Час дійсності** (`valid_from`, `valid_to`) — коли факт тримається у світі.
Підстанція, зруйнована 3-го і про яку повідомили 9-го, була зруйнована 3-го, а
відомо зруйнованою — з 9-го; розбір знеструмлення потребує першого, щоб
відновити мережу, і другого, щоб судити, чи можна було встигнути.

```
GET /api/platform/graph?asOfSeq=1240          # що ми знали на цій ревізії
GET /api/platform/graph?asOf=2026-09-09T00:00:00Z
GET /api/platform/graph?validAt=2026-09-03T00:00:00Z   # як стояла мережа
GET /api/platform/graph?asOf=…&validAt=…      # обидві разом
GET /api/platform/graph/diff?from=1200&to=1240
```

Курсорів теж два, і це не надмірність. Відмітка часу не розрізняє двох змін в
одну мілісекунду, а завантаження робить їх сотнями; тому знахідка справи
закріплює **послідовність** (`graphRevision`) — це різниця між відтворити
аналіз і приблизно його повторити. Звичайне читання графа теж повертає
`revisionHead`: клієнт, який не може назвати ревізію, яку щойно бачив, не може
до неї нічого прикріпити.

Проміжок дійсності напіввідкритий: факт, дійсний «до» моменту, у цей момент уже
недійсний. Закриті проміжки перекривалися б на одну мить, і кожне підсумовування
через межу рахувало б те саме двічі.

### Дії: те, що знає людина, а фід не дізнається ніколи

Досі писало лише завантаження: платформі міг щось сказати фід, а людина могла
лише читати. Між цим не було нічого — і за бортом лишалася вся категорія
знання, яка є тільки в людини. Аналітик, що стояв біля підстанції, знає, чи
справжня лінія в неї заходить, і не мав куди це сказати.

Дія — це не «дозволити API писати в граф». Кожна:

- **оголошує, що їй потрібно**, і відхиляє неповний виклик на межі, а не
  застосовується наполовину, лишаючи граф у стані, якого жодне завантаження не
  створило б;
- **називає свої передумови** і пояснює відмову словами про світ («це ребро
  вже підтверджено»), а не про код;
- **несе власну вимогу до рівня доступу**: право читати факт і право його
  змінювати — різні права;
- **лягає в ланцюг аудиту й журнал ревізій**, тобто відтворювана й іменна, як
  усе інше тут.

| Дія | Навіщо |
|---|---|
| `confirm_dependency` | Виведене ребро (найближчий сусід, впевненість 0.25–0.35) стає підтвердженим людиною. Спосіб, на якому воно стояло, зберігається, а не затирається |
| `mark_damaged` / `mark_restored` | Момент виходу з ладу пишеться як **час дійсності**, тож мережу можна відновити такою, якою вона була під час аварії |
| `link_same_as` | Тотожність записується звʼязком, а не злиттям: злиття знищує докази на власну користь, а рішення про тотожність буває помилковим |
| `declassify` | Зниження рівня. **Дві людини, завжди** |

Розсекречення — єдиний тут контроль, який не просто «відмовляє за
замовчуванням»: його не можна виконати наодинці взагалі. Пропозиція
подається, і схвалює її **інший** принципал, під власним поглядом і з повторною
перевіркою передумови — бо між пропозицією і схваленням світ рухається.
Пропозиція має строк: постійна пропозиція послабити систему — найлегша річ
у світі, щоб схвалити її ненароком через три тижні.

```
GET  /api/platform/actions
POST /api/platform/actions/<id>                       # 200 застосовано, 202 подано
POST /api/platform/actions/pending/<id>/approve
POST /api/platform/actions/pending/<id>/withdraw
```

### Відмова за площею, N-1-1 і черговість відновлення

Критерій N-1 питає: «що буде, якщо відмовить оцей вузол». Для мережі, що
старіє, це правильне питання. Для мережі під ударами — ні: приліт не вибирає
один вузол зі списку, він знімає **все в радіусі**, разом із лініями, що йшли
повз. Підстанція і резервна лінія за два кілометри від неї — не дві незалежні
відмови, а одна.

`simulateAreaOutage` і `rankAreaContingencies` перебирають **епіцентри**, а не
вузли. Різниця не косметична: мережа, що витримує будь-яку одиничну відмову,
розсипається від одного удару по вузлу, поруч з яким стоїть її ж резерв.

`rankSecondFailures` рахує N-1-1. Диспетчерське N-1 говорить про мережу в
повному складі, а мережа під ударами в повному складі не буває майже ніколи:
один вузол у ремонті, другий знищено місяць тому. Запас, порахований по повній
схемі, у цьому стані вже витрачено.

`planRestoration` дає черговість ремонтів. Задача — максимальне покриття,
NP-складна; жадібний вибір гарантує не менш ніж (1 − 1/e ≈ 63%) від найкращого
і рахується швидше, ніж триває сама аварія. Кроки перераховуються після
кожного вибору: поки станція лежить, ремонт підстанції не повертає нікого, і
її цінність зʼявляється лише другим кроком.

Наслідки описуються не числом вузлів, а тим, що можна назвати: розподілом за
секторами, **поіменним** переліком лікарень і водоканалів, і втраченою
генерацією в МВт. Останнє рахується лише по станціях, де `capacityMw` **є в
джерелі**; тег `plant:output:electricity` заповнений в OSM не скрізь, тож
число завжди занижене, і поруч стоїть `capacityUnknownFor` — по скількох воно
не пораховане взагалі. Оцінювати потужність за типом станції означало б видати
припущення за замір.

Заміряно на синтетичній мережі розміру українського (4000 обʼєктів, 3900
ребер): перебір 600 епіцентрів — 48 мс, N-1-1 — 24 мс, план відновлення —
33 мс. Перша версія перебору збирала граф наново на кожного кандидата й
витрачала 1.3 с.

### Наскільки можна вірити позначці

У консолі кілька десятків OSINT-каналів, і досі всі важили однаково: позначка
з однієї новинної стрічки давала той самий рівень, що й позначка, яку
одночасно дали три канали спостереження при активній офіційній тривозі. Це не
обережність — це рівно та помилка, через яку операційні сповіщення перестають
читати: коли все «критичне», критичного немає.

Оцінка йде за кодом Адміралтейства (STANAG 2511): дві **незалежні** осі —
надійність джерела (B–F) і достовірність відомості (1–6). Дві, а не одна,
бо надійне джерело може передати чутку, а сумнівне — сказати правду.

Чого тут навмисно немає — **оцінок конкретних каналів, виставлених нами**.
Присвоїти реальному медіа-ресурсу бал довіри означало б зробити твердження про
нього без підстав. Надійність виводиться лише з двох речей, і обидві
перевіряються: **роль каналу в нашому ж переліку** (доданий як канал
спостереження, регіональний чи загальний — структурний факт про список, не
судження про видання) і **підтвердження** — скільки незалежних джерел сказали
те саме. Друге робить основну роботу: три перекази одного джерела — це одне
повідомлення, а не три.

**Напрямок відмови тут протилежний до решти системи.** У контролі доступу
сумнів вирішується відмовою: не показати зайве дешевше, ніж показати таємне.
У попередженні про повітряну загрозу навпаки — пропущений удар коштує більше,
ніж зайва тривога. Тому рівень **знижується лише за наявності підстав**:
джерело відоме як таке, що переказує, **і** ніхто його не підтвердив. Невідома
роль підставою не є — це невідомість, а не погана якість.

### Реєстр компаній: люди за контрагентами

Prozorro дав платформі договори. ЄДР дає людей за контрагентами — половину, яка
перетворює «ця компанія виграла багато робіт» на питання, варте запитання.

```
POST /api/platform/ingest/edr    # файл реєстру як є, base64; CONFIDENTIAL
```

**Задеклароване — не приховане.** Онтологія несе `HIDDEN_BENEFICIARY_OF` вагою
30 балів, і підключити до неї поле `BENEFICIARIES` було б очевидним ходом і
було б помилкою: реєстр тримає власність, яку компанії **розкрили, бо цього
вимагає закон**. Оцінювати розкриття як приховування означало б покарати кожну
законослухняну компанію в країні й сказати аналітикові протилежне до правди.
Тому задеклароване володіння має власний звʼязок `BENEFICIARY_OF`, а
`HIDDEN_BENEFICIARY_OF` лишається для власності, яку **знайшли**, а не подали.

Ознакою є не володіння, а **форма розкриття**: комерційна компанія, що подала
шаблонну причину відсутності кінцевого власника, або та, чий засновник сидить
у юрисдикції, де ланцюг власності перестає бути простежуваним. Це властивості,
а не вироки; скільки вони важать, вирішує `config/risk_signals.json`.

**Імʼя не є тотожністю.** Реєстр не дає бенефіціарові податкового номера — лише
імʼя, іноді громадянство. Двоє людей на імʼя Іванов Іван Іванович — це двоє
людей, і граф, що зводить їх в один вузол, вигадав звʼязок між двома живими
людьми, у яких його немає. Це найгірша з доступних тут помилок. Тому людина
ключується **на компанію**: `person:edr:<едрпоу>:<імʼя>`. Те саме імʼя у двох
компаніях — два вузли, а резолвер пропонує їх парою, яку людина підтверджує
дією `link_same_as` — записано, оборотно, іменно.

**Персональні дані — не відкриті дані.** Реєстр публічний, але граф названих
осіб з їхніми частками — інший обʼєкт, ніж карта підстанцій, і не має читатися
кожним ключем, що читає карту. Люди та їхні звʼязки типово йдуть на INTERNAL і
в коло `personal-data`. Розгортання може вирішити інакше — але явно.

**Кодування.** Реєстр публікується у windows-1251, а ні Node, ні Bun його не
декодують: `TextDecoder` підтримує цю мітку в браузері й кидає
`ERR_ENCODING_NOT_SUPPORTED` на сервері. Це **гарна** відмова. Погана — обхід,
до якого тягнеться рука наступним: прочитати байти як UTF-8, що не помиляється
взагалі й перетворює кожне українське імʼя на кашу, яка доїжджає до графа з
виглядом поганих вихідних даних. Тому декодер живе в конекторі, а таблиця
згенерована з еталонного кодека, а не набрана руками, і звірена з ним у тестах.

Перевірено на 1273 справжніх записах реєстру: 4066 вузлів і 2824 ребра під
поглядом із доступом до кола, 2362 і 1097 — назовні; 211 заяв про відсутність
власника, 61 засновник у непрозорій юрисдикції, 5 однойменних пар, які
резолвер запропонував і жодної з яких не злив.

### Конфлікт інтересів: візерунок, який має форму шляху

`self_dealing_pattern` важить 35 балів — найбільше у файлі сигналів — і
визначений як одна сутність, що тримає і `AWARDED_CONTRACT`, і
`HIDDEN_BENEFICIARY_OF`. Зі справжніми даними з обох боків виявилося, що в
людському випадку він спрацювати **не може**, і не через помилку: особа не
присуджує контрактів, це робить організація. Звʼязки висять на різних вузлах,
тож правило, що дивиться на власні ребра одного вузла, шукає там, де візерунка
не буває.

Справжня форма — шлях у три кроки:

```
особа --(керівник)--> замовник --(AWARDED_CONTRACT)--> постачальник
   \                                                        /
    \------------------(бенефіціар)------------------------/
```

```
GET /api/platform/analytics/conflicts?minAmount=1000000
```

Окремий маршрут, а не куток `/analytics`: «хто стоїть на обох кінцях договору»
— питання, що має форму звинувачення проти названих людей, і воно має ставитися
навмисно й лишати власний слід у журналі читань.

**Чому більшість знахідок буде «непідтвердженими» — і чому це правильно.**
Люди з реєстру ключуються на компанію, бо імʼя не є тотожністю. Тому два кінці
шляху — зазвичай два різні вузли з однаковим прізвищем, і зʼєднати їх означає
**ухвалити рішення**: дія `link_same_as`, записана з тим, хто її ухвалив і на
чому. Тому підтвердженою знахідка стає лише після цього рішення, а решта
повертається окремим списком із названим питанням про особу. Вважати однакові
прізвища однією людиною означало б виготовити звинувачення проти живих людей із
збігу написання. Два списки не змішуються ніколи: непідтверджений — це черга
питань про тотожність, а не черга підозрюваних.

Друга форма — `commonOwnership`: одна особа за кількома постачальниками того
самого замовника. Інше питання: не «хто на обох кінцях», а «чи був вибір
узагалі». Конкурентна процедура між компаніями зі спільним власником — класичний
спосіб поставити конкуренцію, і жоден показник окремого договору його не бачить.

### Інструменти агента: право перевіряється на кожному виклику

`InvestigatorAgent` виконує одну незмінну процедуру: пошук, розвʼязання
якорів, два кроки обходу, іноді обчислення, переказ. Вона надійна, і її стеля
низька: відповідає на питання, під які написана, і кожне нове питання означає
новий код усередині агента.

Реєстр інструментів (`platform/agents/analyst/tools/`) перевертає це. Кожна
здатність оголошує, що робить, які аргументи бере і чого вимагає від
викликача; послідовність вибирає планувальник — людина, детермінована
процедура або модель.

```
GET  /api/platform/tools            # каталог із поясненням, чого бракує
POST /api/platform/tools/<name>
```

Безпечним, а не просто гнучким, це робить місце, де стоїть перевірка прав.
Викликач не отримує «доступ до платформи», щоб далі ходити всюди: **кожен**
виклик наново звіряє рівень із вимогою саме цього інструмента, і кожен
інструмент читає крізь погляд викликача. План, що дійшов до інструмента, на
який прав немає, падає на цьому кроці з поясненням, виконавши ті кроки, на які
права були.

Це важить найбільше, коли планувальник — модель: її можна вмовити **спробувати**
будь-що, але не можна вмовити мати допуск, бо перевірка читає принципала, а не
план.

**Жоден інструмент тут не пише, і це структурно.** Зміни графа йдуть через
`/api/platform/actions`, де є передумови й правило двох осіб. Розділення
означає, що в планувальника немає шляху до запису взагалі — не політика, яку
можна обійти вмовлянням, а здатність, якої йому не давали.

Обчислення робить запущений код над явно переданим переліком чисел. Правило,
на якому стоїть увесь слідчий агент, — мовна модель ніколи не рахує число, їй
його показують, — переживає перехід до плану, який пише модель.

### Набір еталонних питань

`platform/tests/evals/` — регресійна метрика вигадування, а не демонстрація
того, що воно працює. У перевірки заземлення два напрямки відмови, і в
щоденній роботі видно лише один: хибне відхилення дає простішу відповідь,
хибне прийняття дає вигадану, якої ніхто не помітить. Тому набір ганяє
валідатор з обох боків на фіксованому корпусі: правдиві перекази мають
проходити, а **кожна категорія** вигадування — ловитися. Написано таблицею,
щоб новий спосіб збрехати був рядком, а не новим тестом, і щоб частка
проходження була числом, за яким можна стежити.

### Звідки взялася картина, і чи джерело ще каже правду

У консолі є панель стану джерел, і вона бачить лише те звернення, яке щойно
зробила: живе, вантажиться, застаріло, недоступне. Це відповідь на питання «чи
джерело відповідає» і не відповідь на те, що справді коштує: **чи воно ще каже
правду**. Джерело, яке віддає HTTP 200 із третиною своїх звичних рядків, не
лежить. Воно зламане так, що доїжджає до графа, зсуває кожне похідне число — і
має вигляд спокійного дня.

Розрізнити це можна лише історією. `platform/core/lineage/` зберігає для
кожного джерела розмір і хеш вмісту кожної партії, і кожне завантаження
повертає вирок:

| Вирок | Що це означає |
|---|---|
| `first` | перша партія, порівнювати ще нема з чим |
| `normal` | у межах звичного для цього джерела |
| `shrunk` | суттєво менше за звичне — джерело відповіло, але, можливо, не тим |
| `grew` | суттєво більше — ймовірно, розширився набір або межі запиту |
| `unchanged` | вміст побайтово той самий: джерело могло заморозитися |
| `empty` | відповіло і не дало нічого — це не те саме, що недоступне |

Вирок **ніколи не блокує завантаження**: у джерела бувають тихі дні, і відмова
від партії проміняла б проблему нагляду на втрату даних. Це названа
спостережність із базою поруч, щоб людина могла відрізнити «сьогодні менше
пожеж» від «розбір перестав збігатися».

Хеш береться по **вмісту**, а не по відповіді: майже кожен фід міняє щось на
кожному виклику — відмітку часу, порядок, — і хеш, що рухається щоразу, не
відрізняє «дані змінилися» від «змінився конверт». Медіана, а не середнє: один
викид не має зсувати базу.

```
GET /api/platform/lineage                     # стан усіх джерел + підозрілі
GET /api/platform/lineage?source=<name>       # історія партій + що з них у графі
GET /api/platform/lineage/entity/<id>         # на яких партіях стоїть ця сутність
```

### Журнал аудиту, який переживає власне зростання

Поки ланцюг записував лише те, що робили агенти, тримати його цілком у памʼяті
було нормально. Запис того, що **читали люди**, змінив криву: журнал тепер росте
разом із трафіком, а слід, який перетворюється на проблему з памʼяттю, — це
слід, який зрештою вимикають. А з ним зникає властивість, на якій стоїть решта
системи.

У памʼяті лишається покажчик, а не вміст: один байтовий зсув на запис плюс
актор і дія як маленькі цілі в словнику тих кількох значень, яких вони взагалі
набувають. Самі записи читаються з диска за зсувом. Фільтрація за актором і
дією — те, за чим фільтрує маршрут аудиту, — лишилася в памʼяті, тож
сторінкування не вироджується у сканування файлу.

Заміряно на 100 000 записів того розміру, який система справді пише (32.6 МБ),
кожна версія в окремому процесі, з примусовим збиранням сміття:

| | утримувана памʼять | старт | сторінка | `verify` |
|---|---|---|---|---|
| було | 90.0 МБ | 185 мс | 0.4 мс | 336 мс |
| стало | **11.9 МБ** | 255 мс | 4.5 мс | 599 мс |

Ціну названо, а не сховано: `verify` став удвічі повільнішим, бо раніше він
проходив уже розібрані обʼєкти — тобто виглядав дешевим лише тому, що памʼять
за нього заплатили наперед. Обмін такий: 300 мс на операції, яку роблять на
вимогу, проти 78 МБ, які тримаються завжди.

### Подорож у часі, яка не дорожчає з історією

Відтворення минулого стану програвало журнал ревізій із нуля. Заміряно на
200 000 ревізій (44.7 МБ — приблизно рік щоденних оновлень українського
набору): 500 мс на старт і 795 мс на відновлення голови, обидва лінійно.
Можливість, вартість якої росте з історією, — це можливість, якою перестають
користуватися.

Виправлено з двох боків. У памʼяті лишається покажчик, а не ревізії: 78.4 →
**11.1 МБ** на 200 000 ревізій. І відтворення починається з найближчого
знімка, а не з нуля.

**Знімок пишеться не за розкладом, а коли окупається.** Це не дрібниця: чи
окупається він, цілком залежить від навантаження. Заміряно на двох формах по
200 000 ревізій:

| Форма навантаження | Журнал | Знімки | Відтворення голови |
|---|---|---|---|
| оновлення тих самих 4109 обʼєктів (те, що робить платформа щодня) | 44.7 МБ | 5.0 МБ | 795 → **15 мс** |
| ревізія на кожну нову сутність | 45.4 МБ | **226 МБ** | без пришвидшення |

У другій формі знімок завбільшки з журнал, що його породив, і завантаження
сповільнювалося вчетверо. Тому рішення ухвалюється на кожній межі: якщо стан
має більше вузлів і ребер, ніж було ревізій від останнього знімка, знімок
коштував би дорожче за відтворення, яке він замінює, — і не пишеться.
Порівняння за лічильниками, а не за серіалізованими байтами: серіалізувати
стан, щоб зʼясувати, чи варто його серіалізувати, — саме та пастка, якої це
уникає.

Знімок — це кеш, і поводиться як кеш: зіпсований знімок не валить запит, а
відкидається на користь повного відтворення. Тест ставить саме це, і ще один
перевіряє головне: відтворення зі знімка дає **точно те саме**, що й повне.
Швидша реконструкція, яка відрізняється від повільної, реконструкцією не є.

### Джерело як документ, а не як клас

Кожен конектор тут писався руками й кожен наново вирішував те саме: як дістати
поле, як зібрати ідентифікатор, під якою міткою писати, звідки це взялося, з
якого моменту факт чинний. Для трьох джерел це нормально. Для тридцяти це
означає тридцять місць, де інваріант можна забути, — і забудуть його саме там,
де ніхто не читав код уважно.

Тому підключення фіду більше не є написанням коду. Це **документ**, який
описує відображення записів у сутності та звʼязки:

```
GET  /api/platform/sources                 # що система вміє приймати
POST /api/platform/sources                 # додати відображення; CONFIDENTIAL
POST /api/platform/ingest/source/<id>      # виконати його над партією
```

Маніфести лежать у `platform/config/sources/` і читаються на старті. Одне
зіпсоване відображення не валить розгортання — воно повертається у списку
помилок разом зі станом здоровʼя, бо система, що відмовляється стартувати через
одруківку в фіді, яким ніхто не користується, — це система, з якої знімуть
валідацію.

**Чого маніфест не може.** Він не може виконати код. Набір перетворень
(`trim`, `number`, `iso_date`, `wkt_lat`, `last_path_segment`, …) **закритий**,
і кожне перетворення тотальне та без побічних ефектів. Відображення, яке вміє
запускати довільний вираз, уміє все — і перестає бути документом, який
переглядають, стаючи програмою, яку доводиться перевіряти на безпеку, і то з
правами самої інгестії. Коли фідові потрібне щось нове, відповідь — назвати
перетворення тут і покрити тестом, а не відкрити люк.

Він також не може вирішити, під якою міткою піде запис. Рівень — мінімум із
задекларованого джерелом і допуску того, хто запускає; кола — перетин із тими,
що людина справді має; походження (`provenance_source`, версія маніфесту) і
`sourceDocId` проставляються виконавцем на **кожному** вузлі та ребрі. Сутність,
позначена `personal`, піднімається щонайменше до INTERNAL і в коло
`personal-data` — навіть якщо той, хто вантажить, у цьому колі не перебуває.
Відмовитися позначити, бо викликач сам не в колі, означало б натомість
опублікувати людей, а це хибний напрямок відмови.

Звʼязки звіряються з онтологією **при реєстрації**, а не порядково. Це різниця
між помилкою відображення, яку бачить її автор, і помилкою, що зʼявляється по
одній на рядок о третій ночі, має вигляд поганих вихідних даних і лишає фід
підключеним наполовину.

**Дві речі, яких у мові не було, поки не приїхали справжні дані.** `const`
окремо від `fallback`: сталу писали як `fallback`, а той спрацьовує лише коли
шляху немає, тож поле мовчки зникало на всіх записах, де шлях був. І
`optional` для сутності: Wikidata називає оператора для 7 станцій із 244, тож
чесний виконавець нарахував 237 «пропущених» записів — звіт, у якому справжня
поламка не має шансу бути поміченою.

Перевірено на живій вибірці Wikidata: 244 рядки → **152** унікальні станції,
99 із потужністю, разом **55 469,7 МВт** (Запорізька АЕС — 5700, Запорізька
ТЕС — 3650, Вуглегірська ТЕС — 3600), 7 ребер `OPERATED_BY`, 0 пропущених, 0
відхилених. Це закриває конкретну прогалину: потужність була відома майже
жодному обʼєкту з OSM, а половина моделі наслідків відмови рахує саме її.

### Шарів критичної інфраструктури в продакшні немає

Консоль будувалася навколо карти обʼєктів: підстанції, електростанції, лінії
110 кВ+, а поверх них — рейтинг критичності, розбір відмови N-1 і кореляція
повітряних загроз із тим, що під ними. Разом це відповідь на питання **який
обʼєкт вивести з ладу, щоб наслідки були найбільшими**. Вона потрібна тому, хто
відновлює мережу, і так само придатна тому, хто її ламає, а публічний сайт не
розрізняє цих двох.

Тому шари вимкнені. Не сховані — **не віддаються**.

```
INFRA_LAYERS=on    # єдине значення, що вмикає; будь-яке інше — ні
```

**Вимикач читається на сервері.** Дані по обʼєктах приходять виключно через
серверні функції — браузер ніколи не ходить до Overpass сам, — тож достатньо,
щоб відмовляв сервер. Прапорець у клієнтському бандлі вимкнув би малювання;
серверний вимикає саме існування даних по той бік HTTP. Перше обходиться
інструментами розробника, друге — ні.

**Найбільше важив не вимикач, а опорний перелік.** `infra-seed.ts` — 90
ключових обʼєктів країни з координатами й операторами — імпортувався
**статично з клієнтського маршруту** заради миттєвого показу, поки вантажиться
Overpass. Тобто їхав у бандлі до кожного відвідувача, незалежно від того, чи
хтось його запитував, і незалежно від будь-якого вимикача. Заміряно на збірці:
чанк маршрутів 92 647 → **76 265 байт**, згадок «Укренерго» в клієнтських
ресурсах 11 → **0**, «Енергоатом» 4 → 0, «Укргідроенерго» 9 → 0. Тепер він
вантажиться динамічним імпортом усередині обробника й лишається на сервері.

**Платформа теж.** Вимкнути лише показ означало б, що граф усе одно
наповнюється тим самим — і вимикач стає косметичним. `/api/platform/ingest/infraua`
відповідає 403, а маніфест, що оголосив `criticalInfrastructure: true`
(`wikidata-power-plants`, `wikidata-dams`), не реєструється взагалі: не
завантажується на старті, не зʼявляється в `/sources`, не має куди приймати.
Оголошує це сам маніфест, а вирішує розгортання — фід каже, що несе, і не він
вирішує, чи це тут прийнятно. Населені пункти (`wikidata-settlements`)
лишаються: населення — не інфраструктура, і змішати їх означало б забрати
разом із цілями ще й підставу рахувати наслідки в людях.

**Невідоме читається як вимкнене.** Сторінка збирається на сервері раніше, ніж
запит устигне відповісти, тож усталене значення «увімкнено» давало б кадр із
уже намальованою обстановкою шарів. Через це увімкнений шлях мусить
проставляти `disabled: false` **явно**: поки він лишав поле порожнім, він був
невідрізненний від «ще не відповіли» — і вимикач не вмикався назад. Зловлено
перевіркою в браузері, а не міркуванням.

Що лишилося в продакшні: повітряні тривоги, лінія фронту (DeepState), пожежі
(FIRMS), сейсміка й події (USGS, NASA), космічна погода, збої звʼязку, погода.
Обстановка — так; перелік того, що варто вразити, — ні.

### Вимикач, який крутять із телефона

Змінна оточення — правильне місце для рішення «чи можна взагалі» і непридатне
для щоденної ручки: Worker не може переписати власне оточення, тож команда з
чату змінити її не здатна, а зміна в дашборді потребує рестарту сервісу.

Тому вимикач складається з двох частин, і шари віддаються лише коли **обидві**
кажуть «так»:

| | Де живе | Хто крутить | Що означає |
|---|---|---|---|
| **Дозвіл** | `INFRA_LAYERS=on` у дашбордах | власник розгортання | чи можна це тут узагалі |
| **Ручка** | файл на диску платформи | оператор: бот, API | чи показуємо зараз |

Композиція саме «І», а не «АБО», бо ролі різні. Ручка, здатна ввімкнути те,
чого власник розгортання не дозволяв, — це не ручка, а обхід. Зворотний бік
важливіший: **вимкнути можна завжди**, кожною частиною незалежно. Вимикач, що
може заклинити в положенні «увімкнено», гірший за його відсутність.

```
/layers            # стан: обидві половини нарізно
/layers on|off     # оберт ручки
/purge             # що лежить у графі від фідів інфраструктури
/purge yes         # прибрати
```

**Дві половини показуються нарізно навмисно.** «Вимкнено» має два різні
наслідки: закриту ручку крутить та сама команда, а закритий дозвіл — лише
дашборд. Одне слово на двох відправило б власника крутити не те.

**Реєстр вирішує на ходу, а не при старті.** Спершу маніфести інфраструктури
просто не завантажувалися, коли вимикач закритий, — і кожен оберт ручки
вимагав би рестарту. Тепер вони завантажуються завжди, а `list()` і `get()`
питають вимикач у момент запиту. Перевірено на працюючому сервісі: після
`/layers on` фіди зʼявляються в `/sources` без рестарту.

Прибирання вже завантаженого — **окрема** дія, і це не формальність.
«Більше не приймаємо» і «того, що прийняли, більше немає» — різні обіцянки, і
друга незворотна. Тому `/purge` спершу показує, що прибере, і прибирає лише
після явного підтвердження. Перелік партій береться **з самого графа**, а не з
зашитого списку імен: партію могли завантажити під будь-яким іменем, і
здогадка тихо лишила б її на місці. Вимкнена ручка при цьому не ховає партії
від чистки — інакше вимикач приховував би саме те, що хтось намагається
прибрати.

**Власник — змінна оточення, не константа в коді.** `TELEGRAM_OWNER_ID` двічі
навмисно: це персональні дані, яким не місце в публічному репозиторії, і це
елемент контролю доступу — міняти його має бути можна, не випускаючи збірку.
Поки він не заданий, адміністративних команд немає **ні в кого**; власник
звіряється з тим, **хто написав**, а не з чатом, бо в групі `chatId` спільний.
