## Звʼязок із платформою Palanter

Консоль може передати свою картину — обʼєкти, події та звʼязки живлення разом
із їх походженням — у аналітичну платформу, де вони підпадають під онтологію,
рівні доступу і журнал аудиту. Похідні оцінки (критичність, наслідки відмов)
не передаються навмисно: у платформі вони перераховуються з графа.

Дві змінні середовища **на сервері** вмикають кнопку «Передати картину»:

```
PLATFORM_API_URL=https://<ваш-palanter>.up.railway.app
PLATFORM_API_KEY=<ключ із PLATFORM_API_KEYS>
```

Ключ читається лише в серверній функції й у клієнтський бандл не потрапляє.
Без цих змінних консоль працює як раніше — кнопки просто немає, це штатний
стан, а не помилка.

На боці Palanter потрібно дозволити походження консолі в `CORS_ORIGINS`.

## Перевірка

```
bun install
npm run typecheck   # tsc --noEmit
npm run lint        # eslint + prettier
npm test            # bun test src/
npm run build
```

Тести написані під вбудований рушій Bun (`import { describe, expect, it } from "bun:test"`),
бо цим самим Bun проєкт і збирається. `vitest` у залежностях немає — запуск його
ззовні впаде на всіх файлах, і це не поламані тести, а не той рушій. Спосіб
запуску один: `npm test`.

Тими самими чотирма командами і в тому самому порядку йде CI
(`.github/workflows/ci.yml`), тож локальний прогін означає те саме, що й
перевірка на сервері.

## Розгортання на Railway

Консоль розгортається у двох місцях одночасно, і це навмисно: Lovable збирає
її під Cloudflare Workers, Railway — під Node. Другий шлях потрібен, бо на
ньому буде Telegram Mini App, якому потрібен стабільний власний домен.

Різницю робить одна змінна середовища **на боці Railway**:

```
NITRO_PRESET=node-server
```

Без неї збірка йде під Cloudflare (це типова ціль пресету
`@lovable.dev/vite-tanstack-config`), контейнер не слухає `PORT`, і Railway
віддає 502 при цілком успішній збірці. Саме так це й виглядало спочатку:
статус деплою `SUCCESS`, а сторінка недоступна.

Усередині власного середовища Lovable ця змінна ігнорується — пресет її
навмисно вичищає, — тож увімкнути її на Railway безпечно: збірку для Lovable
вона не зачіпає.

Запуск на Railway: `npm start` (`node .output/server/index.mjs`). Порт бере з
`PORT`, який Railway задає сам.

## Платформа (`platform/`)

Аналітична платформа — онтологія, граф знань із рівнями доступу, ланцюжок
аудиту, пісочниця для обчислень, слідчий агент. Раніше вона жила в окремому
репозиторії `Palanter`; тепер це один продукт і один репозиторій, а `platform/`
— її місце тут.

```
npm run platform:typecheck   # tsc -p platform/tsconfig.json
npm run platform:test        # bun test platform/tests  (203 тести)
npm run platform:build       # компіляція + межа CommonJS
npm run platform:start       # node platform/dist/api/server.js
```

`npm run check` виконує і консоль, і платформу — тими самими кроками, що й CI.

**Чому окремий tsconfig.** Консоль — це ESM зі строгими правилами під браузер;
платформа — CommonJS під Node. Одні налаштування на двох означали б послабити
консоль до рівня, який влаштовує сервер.

**Чому крок збірки, а не просто `tsc`.** У корені оголошено `"type": "module"`
— цього вимагає консоль. Node дивиться на найближчий package.json, тож
скомпільований CommonJS вантажився б як ESM і падав на першому `exports.`.
`platform/build.mjs` кладе у `platform/dist` вкладений package.json із
`"type": "commonjs"` — межа двох модульних систем проходить по каталогу.

Тести платформи не потребують jest: у них немає жодного виклику `jest.*`, тож
вони працюють під вбудованим рушієм Bun, як і решта репозиторію.

Змінні середовища: `PLATFORM_API_KEYS` (JSON-мапа ключ → рівень доступу),
`CORS_ORIGINS`, `PLATFORM_DATA_DIR`, необовʼязково `ANTHROPIC_API_KEY`.

## Telegram-бот

`@Radar_UAbot` живе вебхуком у сервісі консолі, а не окремою службою: йому
потрібен публічний HTTPS-домен, який у консолі вже є, а дані, які він показує,
лежать тут само. Окремий сервіс коштував би грошей і додав би мережевий стрибок
між ботом і його ж фактами.

Точка входу — `POST /api/telegram/webhook`, логіка розбору й текстів —
`src/lib/telegram.ts` (чиста, з тестами).

Змінні середовища сервісу консолі:

```
TELEGRAM_BOT_TOKEN=<токен від @BotFather>
TELEGRAM_WEBHOOK_SECRET=<довгий випадковий рядок>
```

Секрет обовʼязковий. Telegram надсилає його заголовком
`X-Telegram-Bot-Api-Secret-Token`; без перевірки будь-хто, хто знає адресу
вебхука — а вона не таємниця, — може надсилати підроблені оновлення. Незаданий
секрет відхиляє всіх: забута змінна не має тихо відкривати вебхук світові.

Кнопка меню бота відкриває консоль як Mini App, і те саме дає кнопка під
повідомленнями — але **лише в приватному чаті**: `web_app` у клавіатурі групи
Telegram відхиляє разом із усім повідомленням, тож у групі текст іде без
кнопки, з посиланням усередині.

```
curl -X POST "https://api.telegram.org/bot<ТОКЕН>/setChatMenuButton" \
  -H 'Content-Type: application/json' \
  -d '{"menu_button":{"type":"web_app","text":"Консоль","web_app":{"url":"https://<домен>"}}}'
```

Реєстрація вебхука після розгортання:

```
curl -X POST "https://api.telegram.org/bot<ТОКЕН>/setWebhook" \
  -H 'Content-Type: application/json' \
  -d '{"url":"https://<домен>/api/telegram/webhook","secret_token":"<СЕКРЕТ>","allowed_updates":["message"]}'
```

## Що на Railway

Два сервіси в одному проєкті, обидва з цього репозиторію:

| Сервіс | Що це | Збірка |
|---|---|---|
| `infraua-hub` | консоль + вебхук бота | Railpack, `NITRO_PRESET=node-server` |
| `platform-api` | API платформи | `Dockerfile.platform` |

`platform-api` створено через API, тож у нього **немає автоматичного розгортання
на push** — тригер створюється лише з інтерфейсу Railway (`deploymentTriggerCreate`
project-токену недоступний). Доки його не додано, платформа розгортається
вручну: у Railway кнопкою Deploy, або мутацією
`serviceInstanceDeploy(..., latestCommit: true)`.

Прапорець `latestCommit` тут не дрібниця: без нього Railway перезбирає останній
*відомий* йому коміт, а не свіжий, і три збірки поспіль падали на вже
виправленій помилці.

Стан платформи (граф, аудит, справи) лежить на томі Railway, змонтованому в
`/data` — те саме значення в `PLATFORM_DATA_DIR`.

### Хто читає: рівень, коло, особа

Рівень доступу (`ClearanceLevel`) відповідає лише на питання «наскільки високо».
Це субординація, а не правило поширення: аналітик із рівнем SECRET бачив усе
SECRET у системі, хоча топологія мережі одного оператора, персональні дані його
персоналу і справа про закупівлю — три різні кола «треба знати».

Тому позначка тепер складається з двох частин: рівень і **компартменти**
(`platform/core/security/Marking.ts`). Читач бачить факт, якщо він допущений
**не нижче** рівня **і** входить у **кожне** коло на цьому факті.

Ключ описується у `PLATFORM_API_KEYS` у двох формах — обидві підтримуються:

```json
{
  "ключ-1": "SECRET",
  "ключ-2": {
    "principal": "olena",
    "clearance": "SECRET",
    "compartments": ["grid-topology"],
    "purposes": ["outage-response"]
  }
}
```

Коротка форма не застаріла — це правильна форма для службового ключа, і саме її
використовують наявні розгортання. Вона дає допуск того ж рівня, **жодного**
кола і власника, названого хешем самого ключа. Тобто оновлення платформи не
змінює мовчки, хто що читає, і не вписує старий ключ у всі кола одразу.

Запис можна позначити лише тим колом, у яке входить сам автор запису. Інакше
можливі два збої, і другий гірший: вигадане коло робить дані нечитними взагалі
(діра в графі, не відрізнна від втрати даних), а запис у чуже коло означає
писати факт, якого ти сам ніколи не побачиш, щоб перевірити.

### Навіщо робиться запит, і що з цього записано

Рівень доступу каже, що людині дозволено бачити. Він не каже, чи цей конкретний
перегляд був частиною її роботи, — а зловживання живе саме там: аналітик із
допуском до мережі, що дивиться підстанцію свого сусіда, лишається в межах
допуску й поза межами роботи. Жодна перевірка за рівнем цього не побачить.

Тому запит може нести заявлену причину заголовком:

```
X-Access-Purpose: outage-response
```

Призначення **не** відкриває даних — це не другий рівень доступу. Воно
привʼязує запит до названої причини, відхиляє причини, під які цей ключ не
видавали, і записує причину в ланцюг аудиту поруч із тим, що повернулося.
Виявлення, не запобігання — і це чесний опис, через який воно коштує заголовка,
а не перебудови.

Перелік причин — у `platform/config/security_policies.json`. Прапорець
`require_purpose` типово вимкнений: увімкнути його, поки жодному ключу не
видано призначень, означало б одномоментно закрити всі ключі від усіх
маршрутів, а контроль безпеки, впровадження якого виглядає як аварія, просто
вимикають. Ключ із власним переліком `purposes` тримається його в будь-якому
разі, тож перехід робиться ключ за ключем.

**Кожне читання тепер у журналі.** Досі ланцюг тримав те, що робили агенти, і
нічого про те, що бачили люди: `GET /api/platform/graph` не лишав жодного
сліду, тож питання «хто вивантажив перелік підстанцій і за яким дорученням»
відповіді не мало. Записується форма відповіді — маршрут (шаблон, без
ідентифікаторів і пошукових рядків), причина, рівень, кола і **кількості**, —
але ніколи сам вміст: журнал, що копіює описувані дані, є другою, гірше
захищеною копією цих даних.

Через це `GET /api/platform/audit` став сторінковим:
`?limit=&before=&actor=&action=`. Перевірка ланцюга (`verification`) охоплює
**весь** журнал, а не сторінку: сторінка, що сходиться, поки змінено давніший
запис, — хибне заспокоєння.

### Стоячі запити: питання, яке не треба ставити вдруге

Консоль уже зіставляє повітряні загрози з обʼєктами — покадрово, у браузері,
і все зникає при перезавантаженні. Це **подання**, а подання не може сказати,
що щось почало мати значення, поки ніхто не дивився.

Стоячий запит — умова, покладена на зберігання й переобчислювана щоразу, коли
надходять дані (`platform/core/alerts/`). Спрацювання потрапляє в чергу
розбору зі станами `new → acknowledged → resolved`: хто ще не дивився, хто
взяв, хто закрив і чому. Ці три відповіді й перетворюють потік подій на
роботу, яку можна передати наступній зміні.

Умови — дані, а не код (`platform/config/alert_rules.json`). Те, заради чого
варто розбудити людину, — операційне рішення оператора, воно змінюється
щотижня і не має чекати на випуск. Кожне спрацювання повертається з доказом:
рядками, які кажуть, **чому саме цей обʼєкт**. Сповіщення, яке не можна
розібрати, привчає відхиляти його — а далі відхиленим буде й те, що спрацювало
правильно.

Дедуплікація — різниця між чергою і потопом: умова, що продовжує триматися
(підстанція нікуди не поділася з-під геозони), збільшує лічильник наявного
запису, а не створює новий. Закритий запис лишається закритим протягом
«тиші» (`reopenAfterMinutes`) і відкривається знову, лише якщо умова
спрацювала після неї — повторення це новина, миготіння ні. Вручну відкрити
закритий запис не можна: відкриває його факт про світ, а не натискання.

Позначка сповіщення — підлога правила, піднята до позначки обʼєкта, що
спрацював. Спостереження саме є формою доступу, тому правило бачить коло,
лише якщо саме в нього вписане, а вписати його може лише автор, який у цьому
колі є. Наслідок названий прямо: закриті дані не під наглядом, доки хтось
зсередини кола не напише для них правило.

```
GET  /api/platform/alerts?state=new&minSeverity=high
GET  /api/platform/alerts/rules
POST /api/platform/alerts/rules              # CONFIDENTIAL і вище
POST /api/platform/alerts/evaluate
POST /api/platform/alerts/<id>/acknowledge
POST /api/platform/alerts/<id>/resolve
```

### Три квадратичні місця

Заміряно на синтетичних наборах розміру українського (4109 підстанцій — це
лише одна категорія):

| Місце | Було | Стало |
|---|---|---|
| Розвʼязання дублікатів, 4000 сутностей | 116 с | 0.2 с |
| Пошук, 5000 документів × 20 запитів | 913 мс | 95 мс |
| Зіставлення за близькістю, 10 500 вузлів | квадратичне | 71 мс |

Перше — не «погано масштабується», а відмова в обслуговуванні власному
маршрутові `/api/platform/analytics`, який викликає це на кожен запит.

Прискорення тут нічого не варте без доказу, що воно нічого не втратило, тож
у кожному випадку тест порівнює швидкий шлях із повільним:

- резолвер — з повним перебором тих самих пар тією ж функцією оцінки;
- пошук — із наївним косинусом, побітово (`toBeCloseTo(…, 10)`);
- гео-індекс — із повним скануванням, на пʼяти радіусах і через межу комірки.

Блокування може відкинути ключ, який перестав розрізняти («підстанція» є в
кожній назві). Це навмисно й **повідомляється** у `resolution` разом із
відповіддю: резолвер, який тихо перестав шукати, гірший за повільний.

### Закупівлі: джерело для половини онтології, яка його не мала

`AWARDED_CONTRACT` і `HIDDEN_BENEFICIARY_OF` існували в онтології з самого
початку, а `self_dealing_pattern` важив 35 балів — найбільше у файлі сигналів.
Джерела не було в жодного. Половина моделі ризику оцінювала звʼязки, які
структурно не могли зʼявитися: смуги й рейтинги рахувалися ні по чому.

Prozorro закриває цю половину. Джерело відкрите, ключа не потребує, і його
записи несуть те, чого не дає зіставлення назв, — код ЄДРПОУ, тобто справжню
тотожність юридичної особи. Вузли ключуються `org:edr:<код>`: та сама компанія
трапляється в цих записах у кількох написаннях, і всі вони — один
зареєстрований субʼєкт.

```
POST /api/platform/ingest/prozorro        # записи, які вже є на руках
POST /api/platform/ingest/prozorro/pull   # витягти вікно з фіду, CONFIDENTIAL
```

Тягне платформа лише на запит: планувальник потребує блокування, а блокування
між перезапусками Railway немає — два примірники, що обходять те саме вікно,
подвоїли б кожну суму в `value_concentration`, і ніщо не виглядало б зламаним.

Присудження — **ребро** з сумою, а не вузол-подія. Це не смак: сигнал
`value_concentration` підсумовує властивість `amount` по ребрах сутності, тож
записане інакше присудження було б невидиме для оцінювання, заради якого фід і
підключався.

Перевірено на 100 справжніх тендерах, і саме це виявило дві помилки, які
синтетичні дані не показували б ніколи: токенізатор пошуку різав українські
слова (знахідка №17), а обидва структурні сигнали ризику вироджувалися на
розрідженому графі (№18). Фікстура в `platform/tests/fixtures/` — теж справжні
записи: форма, яку я вигадав би сам, перевіряла б лише мою уяву.

### Дві осі часу

Граф зберігав лише теперішнє: `upsertNode` перезаписував властивості на місці,
`retractSource` видаляв. Через це три питання, на які така система має
відповідати, відповіді не мали:

- **Що ми знали чотирнадцятого, коли ухвалювали рішення?** Не що відомо
  *зараз* про чотирнадцяте, а що справді було перед аналітиком тоді.
- **Що змінилося з учора?** Картина без попередньої версії дає лише «подивіться
  ще раз і скажіть, чи щось впало в око».
- **Чи можна відтворити цю знахідку?** Справа закріплювала номер у журналі
  аудиту, але граф під нею вже поїхав, і повторний прогін давав інший висновок
  із тим самим походженням.

Осі дві, і плутати їх не можна. **Час запису** — коли платформа дізналася.
**Час дійсності** (`valid_from`, `valid_to`) — коли факт тримається у світі.
Підстанція, зруйнована 3-го і про яку повідомили 9-го, була зруйнована 3-го, а
відомо зруйнованою — з 9-го; розбір знеструмлення потребує першого, щоб
відновити мережу, і другого, щоб судити, чи можна було встигнути.

```
GET /api/platform/graph?asOfSeq=1240          # що ми знали на цій ревізії
GET /api/platform/graph?asOf=2026-09-09T00:00:00Z
GET /api/platform/graph?validAt=2026-09-03T00:00:00Z   # як стояла мережа
GET /api/platform/graph?asOf=…&validAt=…      # обидві разом
GET /api/platform/graph/diff?from=1200&to=1240
```

Курсорів теж два, і це не надмірність. Відмітка часу не розрізняє двох змін в
одну мілісекунду, а завантаження робить їх сотнями; тому знахідка справи
закріплює **послідовність** (`graphRevision`) — це різниця між відтворити
аналіз і приблизно його повторити. Звичайне читання графа теж повертає
`revisionHead`: клієнт, який не може назвати ревізію, яку щойно бачив, не може
до неї нічого прикріпити.

Проміжок дійсності напіввідкритий: факт, дійсний «до» моменту, у цей момент уже
недійсний. Закриті проміжки перекривалися б на одну мить, і кожне підсумовування
через межу рахувало б те саме двічі.
